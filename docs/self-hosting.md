# Self-hosting secret-gardens

The supported deployment is the repo's `docker-compose.yml`: one `app`
container (API + web UI, runs as the non-root `bun` user) and one `redis`
container, with two named volumes. `scripts/setup.sh` generates the required
`.env`.

```sh
scripts/setup.sh [--url https://gardens.example.com]
docker compose up -d
```

## Environment variables

Compose substitutes the required values from `.env` and passes everything
else in `.env` through to the app container.

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `GARDENS_MASTER_KEY` | **yes** | — | Master encryption key (KEK): base64, exactly 32 bytes. Generated by `setup.sh`. **Back it up — losing it loses all secrets permanently.** |
| `BETTER_AUTH_SECRET` | **yes** | — | Session/cookie signing secret, ≥32 chars. Generated by `setup.sh`. |
| `GARDENS_PUBLIC_URL` | no | `http://localhost:3000` | Public URL users reach the instance at. Must match the browser address or sign-in cookies and OAuth callbacks fail. |
| `BETTER_AUTH_URL` | no | `http://localhost:3000` | Written by `setup.sh` alongside `GARDENS_PUBLIC_URL`; compose falls back to it when `GARDENS_PUBLIC_URL` is unset. The app itself reads `GARDENS_PUBLIC_URL`. |
| `PORT` | no | `3000` | API listen port inside the container. |
| `REDIS_URL` | no | `redis://localhost:6379` | Redis connection; compose pins it to `redis://redis:6379`. |
| `GARDENS_DB_PATH` | no | `./data/gardens.db` | SQLite path; the image sets `/data/gardens.db` (the `gardens-data` volume). |
| `GARDENS_WEB_DIST` | no | unset | Directory of the built web UI to serve at `/`. The image sets `/app/apps/web/dist`; unset disables static serving (development). |
| `GARDENS_AUDIT_MAXLEN` | no | unset (untrimmed) | Approximate max entries per audit stream (`XADD MAXLEN ~`). |
| `GARDENS_ADDITIONAL_ORIGINS` | no | unset | Comma-separated extra trusted origins (e.g. `http://localhost:5173` for the Vite dev server). |
| `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` | no | unset | Enable GitHub OAuth. Set both or neither. |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | no | unset | Enable Google OAuth. Set both or neither. |
| `GARDENS_MASTER_KEY_NEW` | script-only | — | Target key for `apps/api/scripts/rotate-kek.ts` (see below). |

CLI-side variables (not server config): `GARDENS_TOKEN` (token for headless/CI
use, takes precedence over stored credentials) and `GARDENS_HOST` (fallback host
when no `--host` flag or `.gardens.json` is present).

Memory note: password hashing is argon2id (~64 MB per concurrent hash) —
give the app container at least 512 MB.

## Backup & restore

A complete backup is **three** things. Any one alone is not a backup:

1. **`GARDENS_MASTER_KEY`** (from `.env`). Without it, both volumes together are
   ciphertext. Store it in a password manager or offline.
2. **The SQLite volume** (`secret-gardens_gardens-data`) — users, projects, memberships,
   tokens, wrapped project keys. Stop the app first so the WAL is
   checkpointed, then copy the database off the volume:

   ```sh
   docker compose stop app
   docker run --rm -v secret-gardens_gardens-data:/data -v "$PWD:/backup" alpine \
     sh -c 'cp /data/gardens.db* /backup/'
   docker compose start app
   ```
3. **The Redis volume** (`secret-gardens_gardens-redis`) — the encrypted secrets, versions
   and audit streams. Either snapshot the volume, or stream an RDB out:
   `docker compose exec redis redis-cli --rdb /data/dump.rdb` and copy it off
   the volume.

> **SQLite alone cannot restore secrets.** Secret ciphertext lives only in
> Redis; SQLite holds the (wrapped) keys and metadata. Losing the Redis
> volume loses all secret values even with a perfect SQLite backup — and
> vice versa: Redis ciphertext is undecryptable without the wrapped DEKs in
> SQLite and the master key.

Restore: recreate the volumes with the backed-up contents, put the matching
`GARDENS_MASTER_KEY` in `.env`, `docker compose up -d`. The app refuses to start
if the key does not match the database (kek_check).

Redis runs with `appendonly yes` + `appendfsync everysec`: a hard crash can
lose at most ~1s of writes. `gardens push` is idempotent — re-push if in doubt.

## KEK rotation (master key)

Rotates the wrapping key. Secrets in Redis are untouched (envelope
encryption: they are encrypted with per-project DEKs; only the DEK wrapping
changes). The script re-wraps every project key — active and retired — and
the boot-check row in one SQLite transaction, and aborts with no changes if
it finds a key wrapped under an unknown KEK.

```sh
# 1. Generate the new key and run the rotation in the deployment context:
docker compose run --rm \
  -e GARDENS_MASTER_KEY_NEW="$(openssl rand -base64 32)" \
  app bun apps/api/scripts/rotate-kek.ts
# (print the key first and keep it: NEW=$(openssl rand -base64 32); echo "$NEW")

# 2. Replace GARDENS_MASTER_KEY in .env with the NEW key.
# 3. docker compose up -d        # restarts the app under the new key
# 4. Back up the new key. The old key no longer decrypts anything.
```

The script is safe to re-run: rows already wrapped with the new key are
skipped. If the app boots with the wrong key it fails fast with a kek_check
error instead of serving 500s.

## DEK rotation (per-project data key)

Re-encrypts a project's current secrets under a fresh data key; old secret
versions keep their (retired) key version and remain readable. Run it from
the project's settings page in the UI, or:

```sh
gardens rotate dek --project <slug> --yes
```

## Audit log growth

Audit streams are untrimmed by default. Set `GARDENS_AUDIT_MAXLEN=100000` (or
similar) in `.env` to cap each stream approximately. To trim manually:

```sh
docker compose exec redis redis-cli XTRIM audit:instance MAXLEN '~' 100000
docker compose exec redis redis-cli XTRIM audit:<projectId> MAXLEN '~' 100000
```

## Single-instance limitation

Run exactly **one** app container. SQLite and the in-process DEK cache are
not shareable across replicas; horizontal scaling is out of scope for v1.
(`docker compose run --rm app ...` for the rotation script is fine — run it
during a maintenance window.)

## Orphaned Redis keys after a crashed project delete

Project deletion removes the SQLite row first, then deletes the project's
Redis keys. If the app dies between the two, `secrets:{projectId}:*`,
`secretver:{projectId}:*`, `secretvctr:{projectId}:*` and `audit:{projectId}`
can remain. They are unreachable through the API and harmless (ciphertext
only, and the wrapped DEK is gone), but you can sweep them manually:

```sh
docker compose exec redis sh -c '
  for p in "secrets:<projectId>:*" "secretver:<projectId>:*" "secretvctr:<projectId>:*" "audit:<projectId>"; do
    redis-cli --scan --pattern "$p" | xargs -r redis-cli unlink
  done'
```

## Hardening

Two compose defaults trade convenience for a softer posture; tighten them
when the Docker host or its network is shared with anything you don't fully
trust:

- **`docker inspect` exposes the master key.** Compose passes
  `GARDENS_MASTER_KEY` to the app container as a plain environment variable, so
  `docker inspect` on the app container prints it to anyone with Docker API
  access (root or the `docker` group). Treat `docker` group membership as
  equivalent to holding the key. For hardened deployments, prefer Docker
  secrets or another env-isolation mechanism (e.g. injecting the key at
  start time from a secrets manager instead of keeping it in `.env`), and
  keep `.env` at mode 600 (setup.sh does this).
- **The bundled Redis is unauthenticated.** It stores ciphertext only (see
  security.md) and compose does not publish its port to the host, but any
  peer on the compose network can read, delete or corrupt that data. If the
  Docker network is not fully trusted (shared hosts, other containers on the
  same network), set a password and keep Redis on an isolated network: add
  `--requirepass <password>` to the `redis` service's `command` in
  `docker-compose.yml` and change the app's pinned `REDIS_URL` to
  `redis://:<password>@redis:6379`.

## Reverse proxy / TLS

Run secret-gardens behind a TLS-terminating reverse proxy (Caddy, nginx, Traefik) in
production:

- Set `GARDENS_PUBLIC_URL` (and `BETTER_AUTH_URL`) to the exact public URL,
  e.g. `https://gardens.example.com` — auth cookies and OAuth callbacks are
  bound to it. Behind TLS, better-auth issues secure cookies automatically
  because the base URL is `https`.
- Proxy all paths (`/` and `/api`) to the app container's port 3000;
  WebSockets are not required.
- Forward `X-Forwarded-For` so failed-login audit entries record real client
  IPs.
- The CLI talks to the same public URL (`gardens login --host
  https://gardens.example.com`).
